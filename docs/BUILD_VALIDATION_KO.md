# v0.3.8 안정성 검증

2026-10-27, 기준 `7df804c`에서 기존 변경과 데이터를 보존하고 진행했습니다. 이전 결과는 [v0.3.7 기록](validation/v0.3.7/BUILD_VALIDATION_KO.md)에 보관합니다. 이 문서 작성 시 **최종 EXE·8시간 검증은 아직 완료 전**이며 완료 결과를 아래에 추가합니다.

## 재현과 수정

이력 미리보기가 전체 데이터를 읽은 뒤 200개만 표시하고, 보고서 내보내기가 GUI와 공유 DB 잠금을 오래 점유하는 문제를 재현했습니다. 표시 범위를 SQL에서 제한하고, 독립 읽기 스냅샷으로 CSV/HTML을 순차 기록하며, GUI는 백그라운드 작업 결과만 표시하도록 수정했습니다. 내보내기 중 이력 창을 닫으면 취소하고 기존 완성 파일을 보존합니다.

| 합성 100만 건 | 수정 전 | 수정 후 |
|---|---:|---:|
| 미리보기 | 21.716초 / private 1.725GB | 0.120초 / 67.5MB |
| CSV 내보내기 | 100.724초 / 1.790GB / GUI 정지 100.744초 | 93.951초 / 75.4MB / GUI 지연 최대 44ms |
| HTML 내보내기 | 107.738초 / 6.176GB / GUI 정지 107.759초 | 111.183초 / 75.2MB / GUI 지연 최대 55ms |

내보내기 속도가 항상 빨라진다는 의미는 아닙니다. 수정 후 CSV/HTML 실행 중 각각 4,211/4,964개의 별도 모니터링 저장이 진행됐고, 단일 쓰기 최대 지연은 41/46ms였습니다. 합성 10만·100만 건의 CSV·HTML 4쌍은 수정 전/후 바이트 길이와 SHA-256이 일치했습니다. 1만 세션 전체 선택·약 101만 관측에서도 200건만 디코딩하며 독립 검토 측정은 0.637초였습니다. 수치는 이 Windows PC의 합성 벤치마크 결과이며 일반 성능 보장은 아닙니다.

## 저장 장애와 통신 복구

- 실제 SQLite `max_page_count` 제한으로 session/poll/event 단계 `SQLITE_FULL` 3개를 발생시켜 롤백과 용량 제한 해제 후 저장 복구를 확인했습니다.
- 자신이 생성한 쓰기 자식 프로세스만 5회 강제 종료하고 완료 확인된 기록, poll/event 원자성, 재시작 후 `integrity_check`·`foreign_key_check`를 확인했습니다.
- 손상된 합성 DB로 실제 CLI 시작을 시도해 종료 코드 6과 원본 바이트 보존을 확인했습니다. 물리 전원 차단 검증은 아닙니다.
- 실제 Paramiko와 루프백 서버, coordinator/pool/SQLite를 통해 TCP 단절·무응답·동일 포트 서버 재시작 각 20회, 실행 중 중지·재시작 20회를 확인했습니다. 다른 대상의 수집 지속, 잘못된 연결 해제/로밍 이벤트 방지, 늦은 결과 저장 방지, 연결/워커 정리를 확인했습니다.
- 동기 DNS resolver가 끝나지 않으면 취소/종료가 대기하는 기존 제한을 확인했습니다. resolver를 시험에서 풀어 준 결과를 OS DNS의 종료 시간 보장으로 해석하지 않습니다.

## 연속 검증기와 독립 검토

새 합성 데이터 폴더 전용 시간제 진단과 외부 Windows 리소스 기록기를 추가했습니다. GUI heartbeat 외에도 대상별 수집 진행, 저장 시작/끝/중간 간격, 실제 경과 시간, DB 무결성, 정상 종료, 실행 해시와 빌드 식별자를 함께 판정합니다. 잘못된 인자·기존 데이터 폴더·중간 창 닫기·수집 정체·초기 데이터만 몰아 저장하기·잘못된 JSON·headless 8시간 허위 판정은 거부합니다. 기록기는 자신이 생성한 프로세스만 종료합니다.

검토 중 발견한 수집 정체 오판과 DB 검사 연결 미해제를 회귀로 재현해 수정했습니다. 독립 재검토는 soak/기록기 68개 통과와 추가 1대 정체·이력 중간 91초 공백·실패 후 즉시 DB 파일 삭제를 확인했고 추가 중요 지적은 없었습니다. 이력 검토에서는 9개 순서/동일 시각/기간/선택 조합의 기존 보고서 행과 동일함을 확인했습니다.
